# 图片智能混排方案

评审状态：见文末评审记录。实现状态：已实施，待真机验收；见[实施说明](图片智能混排实施说明.md)。

## 目标与范围

面向个人相册清理，同时改善三件事：更容易先遇到临时图片；连续看同一时间段的照片以保留回忆线索；不同时间片段之间有变化，避免从最新一路倒着翻。

首版只用 MediaStore 元数据和现有图片分类，不加图片识别模型、OCR、人脸、地点解析、pHash、联网服务、Room、后台扫描或新的浏览历史库。算法只安排展示顺序，不决定照片价值、不自动标记或删除。相机拍的工作资料不能被可靠识别，是明确的能力边界。

这是图片排序专题规则，现役总合同已按已核实现状重建为[产品需求](产品需求.md)与[产品架构](产品架构.md)，二者引用本专题作为数值规则的唯一解释。原工作区已有删除仍保留，不恢复或混入提交，不合并 main。

## 已核实的现状

- `SessionController.rebuild` 调用 `MediaSource.ids`，排除 `ReviewHistory.keptIds`；Random 路径通过 Fisher–Yates 对单张图片洗牌。
- 当前排序为随机、大文件优先、最新优先、最早优先。设置以 `sort_strategy` 保存，全图片/视频共用。
- 图片可统一在照片板，也可拆照片/截图/已保存三板；分类以路径、目录名和文件名前缀为依据，不读取图像内容。`sourceApp` 是预留位，不可当作已经可用的数据。
- `BoardSession` 只接收 ID 序列，负责轮次、标记、保留、撤回和指针；同会话下一轮不重排。默认图片每轮 20 张，设置支持 1～300 张并立即生效。
- 明确保留会持久化；普通浏览和失效项自动跳过不等于保留。会话序列和未结算标记不持久化，离开会话后不保证续看。
- 详情仍按需加载并预取未来 5 张。删除结算和恢复另有系统请求及回查流程，排序不介入。

代码入口均相对 `kadaishan/app/src/main/java/dev/sxc/kadaishan/`：`domain/session/SessionController.kt`、`BoardSession.kt`、`ReviewHistory.kt`，`domain/DomainApi.kt`、`domain/classify/Rules.kt`，`data/MediaStoreDataSource.kt`、`SettingsRepository.kt`，`ui/boards/PhotoCardViewModel.kt`、`VideoCardViewModel.kt` 和 `ui/settings/SettingsScreen.kt`。

## 用户看到的行为

新增排序选项「智能混排」，说明「近期截图更常出现，同一时间段连续看；仅图片生效，视频仍随机」。保留原四种排序。已有选择、缺省键和非法值仍按现有 Random 处理，不静默迁移；用户主动选择智能混排后生效。

例如：前几天的一小段截图 → 上周的一小段照片 → 另一段截图 → 更早的一小段图片。它是规则示例，不承诺每轮都恰好有四段或这些类型。

每次调度最多取 6 张，片段内部从早到晚；大段照片拆成多个小片段，后续片段可能隔着其他事件出现，但同一事件的各片段先后顺序不得颠倒。其他候选不足时，相邻切片可以连续播放，不保证同事件最多只连看 6 张。小段可一次看完。首版不增加“换一段”、分组删除、组级保留或新的卡面控件，避免给现有手势和撤回增加第二套语义。

轮末仍严格按用户设置的张数结束，不为凑完整片段多展示。下一轮接着既定序列走，若轮末切在片段中间，则下一轮继续剩下的部分；改排序/板块模式、退出重入或进程重建后不承诺续接。

## 算法：元数据 → 时间事件 → 小片段 → 混排序列

### 1. 输入、时间与来源

新增轻量 `SelectionRow(id, category, origin, dateTakenMs, dateAddedSec)`，不使用 `MediaItem` 全量装载或逐文件读取。读取 `_ID`、`DATE_TAKEN`、`DATE_ADDED` 和现有分类所需的三列字符串；分类直接复用 `classifyFields`，不另建截图识别规则。

本次 rebuild 固定注入 `nowMs`、本机 `ZoneId` 和 `Random`；扫描结束前不再次取当前时间。有效时间为大于 0 且不超过 now 的时间戳：优先 dateTaken，否则取有效 dateAdded 转毫秒，否则为未知。秒转毫秒先校验范围，避免溢出；未来时间视为无效，不让它永远占据近期池。dateAdded 可能只是导入时间，故这里只叫“时间片段”，不宣称识别了真实事件。

origin 以标准化 relativePath 为先，空时退到标准化 bucketName，再空时取该分类的统一兜底值。标准化复用/提取既有路径规则（统一斜杠、去首尾斜杠和空白、大小写不敏感），不查询来源 App。

先按当前板块与权限范围过滤，排除系统回收站及明确保留的 ID；分类、合并图片板设置与旧路径完全一致。对输入按 ID 去重，不跨图片/视频混池。

### 2. 互斥的三类候选池

年龄按 `(nowMs - effectiveTimeMs) / 24h` 的实际经过时长计算，不用自然日差。时间未知者不算近期。每张候选图片只能属于一个池，按 A → B → C 顺序归属：

| 池 | 条件 | 用意 |
|---|---|---|
| A 近期截图 | 截图，年龄 ≥3 天且 <90 天 | 提高可能已经用完的截图出场机会 |
| B 近期其他图片 | 未进 A，时间有效，年龄 <30 天，且不是年龄 <3 天的截图 | 覆盖近期相机照和保存图片，不能声称识别工作照 |
| C 其他图片 | 剩余全部，包括旧图、年龄 <3 天的截图、无有效时间的图 | 保证不被规则永久排除，给历史照片留机会 |

3 天是降低刚保存资料的推荐强度，不是禁看或自动过期；今天的截图仍可从 C 出现。老截图也不会因为超出 90 天而消失。阈值是待真机体验校准的初值，不做用户可调参数面板。

### 3. 形成近似时间事件

在每个池内，按 `(category, origin)` 分桶，再按 `(effectiveTimeMs, id)` 升序排序。有效时间条目从头向后贪心分组，满足以下全部条件才并入当前事件：同一当地自然日；与前一张时间差 ≤30 分钟；与当前事件第一张时间差 ≤3 小时。否则新开事件。

池或来源不同即不串组，避免截图夹进相机连拍；这是保守的时间邻近推断，不能保证同一事件。阈值相等时可并入，超出才拆。优先保留不同来源的清晰边界，不追求跨来源智能合并。

时间未知条目一张一个事件，不按 ID 假造时间关联。时间字段回退可以使导入图聚在一起，属于已知局限；不额外解析 EXIF 或内容纠正。

每个事件保留内部升序列表，按连续 6 张切片。事件的“下一未输出切片”是调度单位，不建立持久化 eventId，不向 UI 暴露业务承诺。

### 4. 混排调度

各池先将事件按稳定初序排列（最早有效时间、category、origin、最小 ID；未知排在最后），然后用注入的 Random 独立洗牌成事件队列。复现要求相同输入集合、now、时区及种子得到相同序列，不能依赖 Cursor 或 HashMap 的偶然遍历顺序。

使用固定循环槽位 `A → B → C → A`，每个槽位尝试从对应事件队列头输出一个切片。若事件还有后续切片，将它放回本池队尾；否则移除。池空则跳过该槽位，不重复抽取别池补这个槽；持续循环直到所有队列清空。初次从 A 槽开始。

这是 A/B/C 切片机会约为 2:1:1，不是照片张数配额，也不是任意轮数下的比例保证。6 张切片配合 A/B/C/A 的起始顺序，使三个池均非空时，默认前 20 张一定至少各看到一个切片（长度不足则更早轮到下一池）；C 不必等到第二轮。C 也含今天截图和未知时间图片，因此“出现 C”不等于必然出现旧照片；有旧图时仍是随机机会。每轮只有 1～2 张时不承诺同轮覆盖三池。某池空时自然变成其他非空池轮转；全部池空时返回空序列。队列需用 ArrayDeque/索引，不反复删除列表首项。

保证：同一快照内每个候选 ID 恰好输出一次、事件内切片先后不倒置、每个切片内部升序且连续；全部候选最终都能被遍历。不同重建间不保证未处理图片去重，不增加跨会话冷却或“很久没看过”权重。用户明确保留仍永久出池，直至其主动重置保留记录。

### 5. 伪代码

```text
snapshot = readSelectionRows(query, MATCH_EXCLUDE)  // IO，当前可见图片
rows = uniqueById(snapshot) - keptIds
lanes = partition(rows, now)
for lane in A, B, C:
    events = groupByOriginAndTime(lanes[lane], zone)
    queues[lane] = shuffle(stableOrder(events), random)
order = []
while any queue nonempty:
    for lane in [A, B, C, A]:
        if queue[lane] empty: continue
        event = queue[lane].removeFirst()
        order += event.takeNext(6)  // 严格按内部时间顺序
        if event has remainder: queue[lane].addLast(event)
return order  // 只将 ID 序列交给 BoardSession
```

## 代码改动与兼容

| 入口 | 计划修改 |
|---|---|
| 轻量领域模型、`domain/selection/SmartOrder.kt` | 新增纯 Kotlin 的行模型、时间校验、分池、分组、调度；可放同一文件，避免框架化拆分 |
| `MediaSource` / `MediaStoreDataSource` | 新增 `selectionRows(query)` 的真实实现与测试假源实现，单次图片集合查询轻量列；复用板块匹配逻辑，旧 ids 路径不扩列 |
| `SortSpec` / `Sort.kt` | 新增 `Smart`；穷举 when 全部更新。Smart 的 SQL 只用于稳定扫描 `_ID ASC`，真正调度在领域层；保留旧 SQL 表达式行为 |
| `SessionController.rebuild` | 图片且 Smart 才走元数据查询与 SmartOrder，先排除 kept；视频且 Smart 映射为原 Random 路径；其他排序保持原路径 |
| `SettingsRepository` / `SettingsScreen` | 新增 `SMART` 编码和选项说明；旧键和值保持兼容，缺省与坏值仍 Random；Compose 初始值与持久化读取一致 |
| `PhotoCardViewModel` | 接入构建失败可重试状态；详情预取、动作写盘与撤回不改语义 |

`BoardSession` 不改算法/指针/撤回/轮次实现，不在每次滑动或轮末重新分组。图片/视频两端的设置轮界重读仍沿用现状；视频读到 Smart 时只做会话级随机，不调用图片元数据接口。sort_strategy 仍是共享键，设置说明必须明确这个差异。

扫描走 Dispatchers.IO，排序/分组/调度走 Dispatchers.Default，完成后在原控制流中一次性安装 BoardSession，不发布半成品。首次构建与重试共用提交入口：在主线程安装新会话后、第一次 refresh/ready=true 前，无挂起地调用新会话的 updateRoundSize，重放 VM 最新 currentRoundSize，再同步 UI。不能只使用构建开始时捕获的 roundSize，否则加载期间的设置热更新会被旧值覆盖。纯算法循环与扫描需支持协作取消（例如每 256 条检查一次），CancellationException 继续抛出，不降级成空池。沿用现有先构建再 ready 的门禁，加载中不接受卡片动作。

空字段是正常行级降级，时间未知仍入 C。查询返回 null Cursor 或异常不当成“相册已清空”：Smart 入口报可重试加载错误，清理半成品并保持未就绪；屏幕提供重试，仍无权限时走现有权限入口。区分 SecurityException 与其他读取错误，不对整个媒体查询失败静默重试随机，更不重置保留记录。重试重建需单飞并检查 VM 是否仍存活，防止旧结果覆盖新请求。范围内错误 UI 只改图片入口；视频既有加载错误不在本次扩展范围。

普通文件失效继续由现有详情加载自动跳过，外部新增媒体等到下一次既有重建时才进池，不额外加观察器。系统删除请求前的验活、分批、回查，PendingSettlement、恢复入口与修仙奖励条件均不改变。

复杂度 O(n log n) 时间、O(n) 轻量内存，和现有全量 ID 快照同一量级。不承诺常数内存或瞬时首屏；不在会话结束后常驻保存元数据/队列，排序结束仅保留 ID 序列。

## 可验证的验收标准

自动化重点验证以下性质与操作，不以“看起来更智能”替代：

- 输入任意顺序、重复 ID、空池、单池/双池/三池均不死循环；固定上下文与种子结果一致；输出集合恰等于去重后的可见未保留图片，无遗漏无重复。
- 3、30、90 天等号边界、未来/零/空时间、秒毫秒与溢出，dateTaken 优先及 dateAdded 回退；午夜/DST 使用注入时区分组，年龄仍用实际时长。
- 30 分钟、3 小时等号允许，超出分开；自然日、来源、分类、池不同不合并；间隔小但持续一整天不能连成单个事件；相同时间按 ID 稳定排序。
- 25 张同事件输出为 6/6/6/6/1，片段不倒序；片段内不插其他图。全非空且至少各有足够事件时，前四个调度输出槽是 A/B/C/A；默认前 20 张覆盖三池（用 C 全为旧图的样例验证首轮实际含旧图），另测单事件不足 6 张时仍覆盖。单池能够全部输出，相邻切片允许仍是同事件。
- 轮数 1、20、300，以及中途缩小/放大轮次；轮界可切片但下一轮仍接上既定序列，标记/保留/撤回保持原语义；修改排序下一轮生效。另用可挂起假源/构建任务验证加载中 20→1 及 1→300，释放任务后新会话实际 roundSize 与 VM 一致，分别处理 1/300 张进入轮末；首次构建与重试均覆盖。
- Smart 下照片统一/分板模式与旧过滤命中集合相同；PARTIAL 仅可见图片；kept 排除、撤回保留、主动重新查看保留记录照旧；视频 Smart 为随机且不调用 selectionRows。
- null Cursor、权限中途撤销、查询异常、取消扫描/排序、重复重试有明确加载/权限/错误态，不误报“全部清完”，不破坏保留记录或未结算删除事实。
- 本地合成 1 万/5 万条数据验证规模增长、协作取消与 UI 不在主线程计算；记录查询/排序耗时及峰值内存，设备期望 1 万条构建 p95 ≤2 秒、5 万条 ≤5 秒（含查询，不含图片解码，分别至少 20 次，另报冷/热差异）。超过目标则明确记录并优化，不用截断候选集换取达标。纯算法统计不等于真实 MediaStore/设备性能已通过。

真机体验至少覆盖：①几天前多张截图；②同日连续相机照片；③相隔数月的旧照片；④今天截图；⑤同日大量导入；⑥已保留项。观察是否能连续想起一段经历、是否经常看到已过几天的截图、是否仍有旧图出现。没有相关候选时不伪造比例；跨重启重复未决项是本版已披露行为。

回归还需覆盖标记后取消系统确认、回查删除结果、App 内找回、视频浏览/保留、修仙轮次奖励。不增加 INTERNET 或其他权限/依赖；算法验收不能代替系统删除链路验收。

## 取舍与后续边界

该版本选择“截图优先的轻量规则”，而非语义理解：不保证识别临时相机照，不保证一个时间事件真的对应同一件事，长事件只保证切片连续和切片先后，不保证整场活动一次看完。固定 6 张只是单次调度上限，不是自动结算数，也不是可见连续观看上限。

不引入跨会话公平历史，因此反复只看开头就退出，未决图片仍可能再次出现；只有持续浏览同一快照时才保证最终遍历。若实测这一点明显影响体验，再单独讨论跨会话续看，不提前把首版做重。

当前阈值和 2:1:1 比例是可调整常量；后续若修改分池、分组或轮次语义，须同步测试与合同，不靠随机删除倾向或游戏奖励来训练算法。
